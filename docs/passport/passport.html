Архитектурная схема

Как запустить: на чистой Ubuntu 24.04 (4 vCPU / 8 GB): git clone …/mts-devops-k8s && cd mts-devops-k8s && make up (или по шагам: sudo ./scripts/bootstrap-node.sh → ./scripts/deploy.sh → ./scripts/smoke-test.sh). Проверка: curl http://<IP>:30080/ → Hello World!. ~10–15 минут, без ручного создания ресурсов.

3. Ревью работы и потенциальное масштабирование

Главная особенность решения

Доказуемая воспроизводимость: весь путь от «голой» Ubuntu 24.04 до работающего кластера на kubeadm с Gateway API, метриками и логами выполняется скриптами и на каждом коммите прогоняется в CI на чистой ВМ дважды подряд, с ~40 автоматическими проверками каждого требования. Наблюдаемость сквозная: один запрос с X-Request-ID виден в access-логе Envoy и nginx, а его код ответа и задержка — в метриках Gateway в Prometheus.

Самое сложное решение

Выбор хранилища логов для Fluentd: Elasticsearch/OpenSearch (стандарт, но ≥1–2 GB RAM на JVM), Loki (лёгкий, но в официальном образе Fluentd нет плагина — пришлось бы собирать и публиковать свой образ) или VictoriaLogs. Выбран VictoriaLogs: укладывается в ~100 MB RAM на одном узле, принимает JSON lines встроенным HTTP-выводом Fluentd (официальный образ без доработок), даёт полнотекстовый поиск по всем полям, UI и интеграцию с Grafana. Второе непростое решение — публикация Gateway через фиксированные NodePort вместо MetalLB, чтобы не зависеть от сети стенда эксперта.

Известные ограничения (подробно — README §10)

  • Один control-plane узел; публикация через NodePort 30080/30443; хранилище local-path (данные на диске узла, без репликации).
  • TLS на собственном CA для demo.local (для curl — --cacert); metrics-server с --kubelet-insecure-tls; Fluentd работает от root (только DAC_READ_SEARCH).
